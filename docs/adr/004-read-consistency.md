# ADR 004 — Read Consistency Model

**Context:** Need to decide what GET actually guarantees.

**Decision:** Quorum-Confirmed Linearizable Reads: leader confirms leadership via a quorum heartbeat round, then blocks until `lastApplied >= readCommitIndex` (captured at confirmation time) before serving local state. **A newly elected leader additionally commits and applies a no-op entry in its own current term before serving any read (I-023), tracked via an explicit `readReadyTerm` gate checked *before* the read barrier is even captured — not left as an implicit consequence of the barrier wait.** The barrier alone cannot enforce this: it's defined relative to `commitIndex`, which is exactly the volatile value that hasn't caught up yet on a fresh leader, so a `GET` arriving before the no-op completes can capture a trivially-satisfiable barrier (`commitIndex=0`) and slip through. Quorum confirmation alone doesn't prove a fresh leader's `commitIndex` reflects everything previously committed, since `commitIndex` is volatile and Leader Completeness only guarantees the *log* has the old entries, not that the new leader knows they're committed. See `docs/client-semantics.md` for the full protocol (including the explicit gate and required tests) and `docs/architecture.md` for the no-op mechanism.

**Alternatives considered:**
- **ReadIndex** (formal Raft optimization, skips an explicit log entry the same way this design does) — not implemented, named as future work; this project's mechanism is conceptually related but explicitly not claimed to be the formal ReadIndex algorithm. Notably, a correct ReadIndex implementation has to solve the exact same new-leader problem this ADR's no-op solves (Raft's ReadIndex algorithm itself requires a leader to commit a no-op in its current term before its first ReadIndex-based read is safe) — the no-op-commit approach isn't a shortcut around that requirement, it's this project's way of satisfying it using only mechanisms already in scope.
- **Leader lease** (near-zero-latency reads within a bounded time window, relies on bounded clock drift) — closer to production systems like etcd/CockroachDB; not implemented, named as future work.
- **Route every read through the log** (simplest, fully linearizable, but pays full log-replication latency per read) — rejected as unnecessarily slow given the chosen model provides the same guarantee more cheaply.

**Trade-offs:** every GET pays roughly one heartbeat-RTT — expected to be in the same ballpark as SET's replication-RTT cost, an intentional design choice; the actual measured comparison is Phase 10's job (`docs/benchmarks.md`), and any gap between the two is explained from the real implementation rather than assumed away in advance. A newly elected leader additionally pays one no-op commit before its first read can complete — a one-time, per-election cost, not a per-read one.

**Consequences:** the read-barrier step (I-016) is the one piece easy to omit and get subtly wrong — it's the single most-corrected item across this project's review history, called out explicitly for that reason. The new-leader no-op requirement (I-023) is the second most-corrected item, for the same underlying reason: it's easy to prove "quorum confirms I'm leader" and stop there, without separately proving "my commitIndex is caught up."
