# Invariants — Authoritative Reference

Every phase doc (`docs/phases/phase-NN.md`) lists which of these IDs it affects. `CLAUDE.md` treats every ID below as a hard constraint that must never be weakened to make a test pass — see `CLAUDE.md` rule 31. Per `CLAUDE.md`'s source-of-truth hierarchy, this file outranks `docs/architecture.md` and everything below it if the two ever disagree — if a phase doc cites the wrong ID or misdescribes one, this file is authoritative and the phase doc is the thing to fix.

## Raft Safety Invariants (from the Raft paper's own correctness argument)

| ID | Invariant | Statement | Enforced by | Verified by |
|---|---|---|---|---|
| I-001 | Election Safety | At most one leader per term. | One vote per node per term; majority required to win. | Assert `leaderCount(term) <= 1` for every observed term, cluster-wide. **Not** "exactly one" — a term can legitimately have zero leaders (election failed or still in progress); a separate, distinct liveness test asserts eventual election under appropriate conditions. |
| I-002 | Leader Append-Only | A leader never overwrites or deletes entries in its own log — only appends. Conflicting *uncommitted* entries may be overwritten on **followers**, never on a leader's own log. | No truncation code path exists on the leader side at all. | Leader log length never decreases while it remains leader. |
| I-003 | Log Matching | If two logs contain entries with the same index and term, **those entries are identical, and all preceding entries in both logs are identical.** (Not just "preceding entries match" — the entries at that index themselves are also guaranteed identical, which is what makes the property useful.) | `prevLogIndex`/`prevLogTerm` consistency check in AppendEntries. | Unit tests with hand-built diverging logs. |
| I-004 | Leader Completeness | A committed entry from term T appears in every leader's log for all terms > T. This is a property about which entries a future leader's log *contains*, not a description of any particular voting mechanism. | Election restriction: a candidate must have an at-least-as-up-to-date log to win a vote — the exact log-freshness comparison formula that *implements* this restriction lives in `docs/architecture.md`, not here; phases should cite I-004 for "why the election restriction exists" and cite `docs/architecture.md`'s formula separately for "what the check actually computes." | Force an election with a stale-log candidate; assert it cannot win. |
| I-005 | State Machine Safety | If two nodes have applied an entry at the same index, it's the same entry. | Apply only entries ≤ `commitIndex`; `commitIndex` only advances per I-006. | Chaos test: diff applied state across nodes at matching indices. |
| I-006 | Current-Term Commit Rule | A leader only concludes an entry is committed via majority replication if that entry is from its **current** term. Earlier-term entries commit only indirectly. | Commit-index advancement requires `log[N].term == currentTerm` in addition to majority `matchIndex ≥ N`. | Dedicated Figure-8 replay test. |
| I-007 | Term Monotonicity | `currentTerm` never decreases on any node. | One-directional term adoption (`if term > currentTerm`), persisted before any RPC response, checked on all four term-change touchpoints. **On the RequestVote-response touchpoint specifically: the higher-term check must be evaluated and acted on BEFORE any election-generation/role filtering (`electionTerm`, `role == Candidate`) — never the reverse order, since a same-term-only filter would silently suppress a legitimate higher-term response** (`docs/architecture.md`'s RequestVote response handling). | Fuzz RPC terms on all four touchpoints; assert monotonic non-decreasing `currentTerm`. **Explicit ordering test:** a candidate in term T receives a `RequestVoteResponse` with `Term = T+1` — assert step-down and term persistence occur regardless of `electionTerm`/`role` filtering, i.e. the higher-term reaction is not gated behind those checks. |
| I-008 | Minority Cannot Independently Advance Commit | A minority partition cannot independently establish new commitment based on its own local replication acknowledgements. A minority node *can* passively advance its local `commitIndex` when it later learns `leaderCommit` from a legitimate current leader — that is normal follower behavior, not a violation. | Commit and vote-granting both structurally require a real majority for *new* commitment; adopting an externally-provided `leaderCommit` is a distinct, always-allowed code path. | Partition into minority/majority; assert the minority's isolated self-elected leader (if any) cannot commit a new write; separately assert a minority node correctly adopts `leaderCommit` once reconnected. |

## Implementation Safety Properties (must hold in this codebase specifically)

| ID | Property | Enforced by | Verified by |
|---|---|---|---|
| I-009 | `lastApplied ≤ commitIndex`, always | Applier loop only ever advances `lastApplied` toward, never past, `commitIndex` | Invariant assertion in every chaos/integration test |
| I-010 | `commitIndex ≤ lastLogIndex`, always | commitIndex advancement bounded by local log length | Same |
| I-011 | Committed entries are never truncated | Follower conflict-resolution only touches the *uncommitted* suffix; a conflict at or below `commitIndex` is a fatal invariant violation | Test asserting this path is unreachable; explicit halt/panic if reached in test builds |
| I-012 | **`currentTerm` and `votedFor` are durable across a crash, persisted together as one atomic record — and any persistent term/vote transition must be durably persisted before the node emits any RPC whose correctness depends on that transition.** (Renamed and broadened — earlier drafts of this project stated this only in terms of `votedFor`; the full Raft persistent-state requirement covers both fields as a pair, and they must never be observed independently inconsistent after a crash.) This explicitly includes the **candidate's own self-vote**: on starting an election (`currentTerm++`, `votedFor = self`), the node must durably persist that record **before** sending any `RequestVote` RPC to peers, not only before responding to incoming RPCs — otherwise a crash after sending votes but before the fsync completes can cause the node to vote again in the same term on restart. | Durable write (fsync) of the combined record before responding to any RequestVote **and** before sending an outgoing RequestVote after self-voting; format and atomicity/corruption contract fully specified in `docs/architecture.md`'s TermVoteStore section. | Kill-mid-vote fault-injection test (both crash-before-fsync and crash-after-fsync-before-response variants); a dedicated crash-after-self-vote-before-RequestVote-sent variant; corrupt-record-on-startup test (must fail startup safely, per I-020). |
| I-013 | A follower's replication only counts toward `matchIndex` after that follower's own WAL fsync completes | Leader advances `matchIndex[follower]` only upon `success=true`, sent only after the follower's own fsync | Test: delay a follower's fsync, assert `matchIndex` doesn't advance until it completes |
| I-014 | No network I/O — direct or indirect — while holding the Raft mutex | Replication/RPC-handler goroutines release the lock before any network call | Code-review checklist |
| I-015 | The AI layer cannot mutate Raft state, WAL, KV state, or trigger elections/restarts/kills | `internal/ai` has no import path to `internal/raft`/`storage`/`cluster`; depends only on `internal/observability`'s typed surface, which itself depends only on an `EventSink` interface | CI import-graph check + fault-injection test |
| I-016 | A linearizable read requires **all three** of: quorum leadership confirmation, `lastApplied ≥ readCommitIndex` (captured at confirmation time), and re-validation immediately before returning that role/term haven't changed since confirmation. **The successful re-validation step is the read's linearization point** — everything before it establishes the precondition for reading; the read is considered to have logically occurred at that instant, not at the moment the local KV lookup happens a few instructions later. The re-validation and the subsequent KV lookup must be performed as one synchronized unit, acquiring locks in the fixed **Raft mutex, then StateMachine mutex** order (see `docs/architecture.md`'s Concurrency model) — never the reverse, which would both violate the global lock-ordering rule (deadlock risk against the applier) and leave a write free to land between an unsynchronized "check" and "read," making the declared linearization point false. This invariant is necessary but not sufficient on its own for linearizability against **prior leaders' terms** — see I-023, which closes the remaining gap for a newly elected leader via a separate, explicit readiness gate, not merely this invariant's barrier wait. | Read path implements all three steps in sequence, acquiring the Raft mutex and then the StateMachine mutex (never reversed) for the term/role check and the KV read, held continuously across both; losing leadership mid-wait fails/retries the read | Read-barrier test + leadership-change-mid-read test + a test that a write landing between revalidation and KV read (absent the lock) would be caught + a lock-ordering/deadlock test (concurrent GET and Apply, `go test -race`, plus a dedicated ordering assertion) |
| I-017 | A duplicate `RequestID` with a **different** payload (compared by canonical-command hash, not raw bytes) than the original is rejected (`REQUEST_ID_REUSED`), never silently resolved either way | Apply-loop dedup check compares `SHA-256(canonical command encoding)` — the canonical encoding is a deterministic serialization of `{OperationType, Key, Value}`, not `cmd.Payload` taken as opaque bytes, so that two semantically different commands can never collide under an incidental payload-encoding coincidence | Test: same `RequestID`, different payload, assert rejection; test: two commands with different `OperationType`/`Key`/`Value` but a contrived matching raw-payload encoding still hash differently |
| I-018 | **Storage durability failure ⇒ the node fails closed.** If a required durable write (WAL append, WAL fsync, `TruncateFrom`, or `TermVoteStore.Save`) returns an error, the node must not: ACK the corresponding RPC, grant the dependent vote, count the entry toward replication/`matchIndex`, advance `commitIndex`/`lastApplied` based on it, or continue normal consensus operation as if in-memory and durable state still agree. The node transitions to a stopped/failed state rather than attempting to reconcile or roll back partial writes — this is deliberately the simple, safe answer, not a sophisticated recovery subsystem. | Every durable-write call site checks its error return and triggers fail-closed behavior before doing anything else with that write's result. | Fault-injection test: force a `LogStore.Append`/`fsync`/`TruncateFrom`/`TermVoteStore.Save` failure, assert no ACK is sent, no vote is granted, no replication state advances, and the node stops rather than continuing. |
| I-019 | **A pending client write must never resolve as `SUCCESS` solely because its original log index became applied.** If the entry originally appended at that index is superseded (e.g. the leader lost leadership before commit, and a different leader's entry now occupies that index), the original waiter must fail/retry, never return `SUCCESS` for a command that was never actually committed. | The write-completion mechanism is keyed by request identity (`RequestID` + the term/index of the entry the leader actually appended), not by index alone; the applier resolves a waiter only when it confirms the *same* command (matching `RequestID`) was the one actually applied at that index. | Test: leader appends an entry for a request, loses leadership before it commits, a new leader's different entry ends up at that same index and commits — assert the original request's waiter does **not** return `SUCCESS` (it should time out / fail, triggering the normal client-side `TIMEOUT`-retry path from `docs/client-semantics.md`). |
| I-020 | **Corrupt or ambiguous durable term/vote state causes startup failure, never guessed recovery.** `currentTerm`/`votedFor` are persisted as a single checksummed record (format in `docs/architecture.md`); if that record is missing, truncated, or fails its checksum on startup, the node must refuse to start rather than guess a term/vote pair — guessing wrong could directly violate Election Safety (I-001). This also governs **first boot**: if no record exists at all, the node must synthesize and durably persist an initial `{term=0, votedFor="", bootID=1}` record immediately (not merely hold it in memory) — a first boot that returns this default without persisting it is indistinguishable from a corrupted-away record on the next restart and would silently re-issue `bootID=1`, breaking `EventID` uniqueness (`docs/architecture.md`). If that initial persistence itself fails, startup fails. **The node must not expose itself to normal operation or emit any normal-path telemetry (votes, RPCs, `ClusterEvent`s) until its (incremented, on every boot including the first) `BootID` has finished this durable persistence** — this closes the re-use window where a crash between calculating a new `BootID` and its record actually landing durably could otherwise cause the same `BootID` to be reissued on the next restart after having already been observably used. | `TermVoteStore.Load()` returns an error (not a zero-valued default) on any corruption/ambiguity; `Node.Recover()` treats that error as fatal. First-boot path durably persists the synthesized initial record before `Load()` returns success, and startup fails if that persistence fails. `Node.Start()`'s sequencing gates every other startup action behind `TermVoteStore.Load()`/`Save()` completing successfully. | Test: corrupt the term/vote record on disk, attempt startup, assert it fails cleanly rather than starting with a guessed value. Test: first-ever boot (no record on disk) durably persists `bootID=1` and the node observes `bootID=1` for that run; **a subsequent, actual node restart (going through the normal `Node.Start()`/`Load()` path a second time) must observe `bootID=2`, not `1`** — this is the assertion that actually proves the first boot's `bootID=1` was durably persisted to disk rather than merely held in memory and regenerated as `1` again on the next boot (a bug that a test which only re-checks `bootID=1` after the first boot, without a real second boot, would fail to catch). A third restart must then observe `bootID=3`, confirming the increment-and-persist cycle repeats correctly, not just once. Test: inject a failure/delay in the `BootID` persistence step and assert zero events/RPCs/votes are emitted before it completes. |
| I-021 | **A stale or out-of-order AppendEntries *response* is never applied to `nextIndex`/`matchIndex`.** A response may only update replication state if **all three** hold: (1) the node is still `Leader` — a same-term response that arrives after this node has already stepped down to Follower (e.g. because it accepted a same-term AppendEntries from another leader — see I-001/log-matching) must not mutate `nextIndex`/`matchIndex`; (2) `response.Term == currentTerm` — a response with `Term < currentTerm` is ignored entirely, and `Term > currentTerm` triggers step-down (persist term, per I-007/I-012) rather than updating replication indices; (3) the response belongs to the **currently active replication attempt** for that follower. Point (3) exists because the at-most-one-in-flight-per-follower rule (`docs/architecture.md`) bounds outstanding *requests*, but a **timed-out** request is no longer "in flight" from the leader's bookkeeping perspective even though its response can still arrive later — a subsequent request to the same follower can then be sent and be in flight when the earlier, timed-out request's same-term response finally shows up. Without an explicit per-follower monotonic attempt counter checked against the response, that late response is indistinguishable from a response to the current attempt and would be incorrectly accepted. | Per-follower monotonic `attemptID` counter (transport/replicator-internal bookkeeping, need not be on the wire) incremented on every send, compared against the response's originating attempt before acceptance; explicit `role == Leader` guard; explicit term-comparison guard — all three checked before any `nextIndex`/`matchIndex` mutation in the response handler. | Test: simulate a delayed response arriving after the node's term has advanced past the request's term — assert it's ignored. Test: simulate a request timing out, a second request being sent to the same follower, then the **first** request's same-term response arriving late — assert it's ignored and does not mutate replication state (the specific gap the at-most-one-in-flight rule alone does not close). Test: simulate a node stepping down (same term) between sending a replication request and receiving its response — assert the late response, though same-term, does not mutate state because `role != Leader`. |
| I-022 | **`commitIndex` and `lastApplied` are monotonic non-decreasing during normal (non-restart) node execution.** The sole exception is re-initialization to 0 immediately after a crash-restart, before the normal recovery sequence (`docs/architecture.md`) re-establishes them from the current leader — this exception is explicitly volatile-state re-initialization, not a violation of monotonicity *during* a single continuous run. Corollary, stated explicitly because it makes the commit calculation easier to reason about: for a leader during normal operation, `matchIndex[self] == lastLogIndex` at all times (`docs/architecture.md`'s `nextIndex`/`matchIndex` initialization and write-path sections both maintain this). | `commitIndex`/`lastApplied` advancement code paths only ever increase these fields; the only code path that sets them to a lower value is the recovery sequence's initial reset, which happens before the node participates in normal Raft operation again; `matchIndex[self]` is updated in the same step that appends to the leader's own log. | Assertion in every long-running/chaos test: within a single node's continuous uptime (between a start and the next crash/restart), `commitIndex` and `lastApplied` never decrease. Assertion: `matchIndex[self] == lastLogIndex` holds at every checkpoint while a node is leader. |
| I-023 | **A newly elected leader must commit and apply a no-op entry in its own current term before serving any quorum-confirmed linearizable read, enforced via an explicit `readReadyTerm` gate — never as an implicit consequence of the ordinary read barrier.** Leader Completeness (I-004) guarantees a new leader's *log* already contains every previously committed entry, but `commitIndex` is volatile (`docs/architecture.md`'s Recovery path) and resets to a conservative value on election — a new leader has no way to know, from quorum-heartbeat confirmation alone, that its `commitIndex` reflects everything actually committed by prior leaders. The Current-Term Commit Rule (I-006) means a leader can only conclude an entry is committed via its own current-term replication; committing and applying a no-op immediately upon election forces the leader's `commitIndex`/`lastApplied` to catch up to (at minimum) everything previously committed, closing the gap. **Relying on the ordinary read barrier alone to enforce this is insufficient and was an earlier, incorrect draft of this project's own documentation:** a fresh leader's `commitIndex` can start at `0`, so a `GET` arriving before the no-op completes captures `barrier.CommitIndex = 0` and its barrier wait (`lastApplied >= 0`) is trivially satisfied immediately, before the no-op has committed — the read proceeds against a stale `commitIndex` despite I-016's barrier step technically "passing." A separate, explicit readiness marker is required precisely because the barrier is defined relative to the very value (`commitIndex`) that hasn't caught up yet. | Upon transitioning to Leader, a leader-only volatile `readReadyTerm` (Raft-mutex-protected, alongside `nextIndex[]`/`matchIndex[]`) is reset to `0`; the leader appends a no-op log entry in its current term, replicates it to quorum, and waits for it to commit and apply through the normal commit/apply path (I-006/I-005); only once that completes is `readReadyTerm` set to the current term. `GET` checks `readReadyTerm == currentTerm` as its own explicit step **before** capturing a `ReadBarrier` — if not yet ready, it blocks/retries rather than falling through to the barrier wait, which cannot be trusted to reject on its own. | Test A: old leader commits a write and crashes; a new leader is elected; a `GET` issued **immediately** after election (before any client write in the new term) must observe the old leader's committed write. Test B (the one that specifically catches the implicit-barrier bug, and must be present in addition to Test A): a new leader is elected; before its no-op has committed/applied, issue a `GET` — assert it does **not** complete until the no-op commits and applies. Test A alone can pass under a buggy implicit-barrier implementation in timing-lucky runs; Test B cannot. |
| I-024 | **`TermVoteStore` record replacement is crash-atomic: after any crash, recovery observes either the complete pre-write record or the complete post-write record, never a partially-overwritten hybrid — and an orphaned, never-promoted temp file left behind by an interrupted replacement is never mistaken for authoritative state.** `fsync` after an in-place overwrite does not by itself guarantee this — an in-place write can be torn by a crash mid-write, before or during its own fsync. | Write the new record to a temp file in the same directory, `fsync` the temp file, `rename()` the temp file over the existing record (an atomic filesystem operation on POSIX), then `fsync` the containing directory (so the rename itself is durable). Never overwrite the existing record file in place. `Load()` treats the canonical record file as authoritative whenever it is present and valid, regardless of whether an orphan temp file also exists — only `Save()`'s own `rename()` may ever promote a temp file to canonical; a canonical-record-missing-but-temp-file-present state is treated as corrupt (fatal), never auto-recovered by promoting the temp file. | Fault-injection test: force a crash at each of (temp-write-before-fsync, temp-fsync-before-rename, rename-before-directory-fsync, after-directory-fsync) and assert recovery always yields either the exact old record or the exact new record — never a corrupt/mixed one. Orphan-temp-file test: leave a valid `termvote.tmp` alongside a valid `termvote`, assert `Load()` uses only `termvote`'s values, never `termvote.tmp`'s. Missing-canonical-with-orphan-temp test: remove `termvote` but leave `termvote.tmp`, assert startup fails rather than promoting the temp file. |

## How phases reference this file
Each `docs/phases/phase-NN.md` has an "Invariants affected" field listing the relevant IDs from this table. If a phase doc cites the wrong ID or mischaracterizes what an ID means (e.g. describing I-004 as "the log-freshness formula" rather than as the completeness property that formula enforces), that is a documentation bug in the phase doc — this file is authoritative and the phase doc gets corrected to match it, not the reverse.
