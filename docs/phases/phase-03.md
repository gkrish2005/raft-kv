# Phase 3 — Commit, Apply, and Reads

## Goal
The correctness core of the project: advance `commitIndex` safely, apply entries to the state machine (including handling application-level errors correctly), implement the full quorum-confirmed linearizable read protocol including term revalidation, and close the new-leader read gap with a current-term no-op commit.

## Scope
- Commit-index advancement: candidate N = highest index such that a majority (including self) have `matchIndex >= N` AND `log[N].term == currentTerm` (I-006).
- Follower `commitIndex` advancement from `leaderCommit` in AppendEntries — this is also the mechanism by which a **minority** node correctly and harmlessly advances its own `commitIndex` once it reconnects and learns a legitimate `leaderCommit` (I-008 — this is normal behavior, not a violation; see `docs/invariants.md`'s precise I-008 wording).
- Applier loop: whenever `commitIndex > lastApplied`, apply entries in order, advance `lastApplied`. **An application-level error from a committed command does not roll back `commitIndex` or block `lastApplied` — see `docs/client-semantics.md`'s "Application errors are still applied" rule; the log entry is consumed deterministically regardless of whether `Apply()` returns success or an error.**
- Client write path blocks (with timeout) until the entry it created is applied — using the **request-identity-aware `PendingWrite` waiter** from `docs/architecture.md` (I-019), never a naive "wait for index N to be applied." A pending write must fail/retry (surfacing as `TIMEOUT` to the client) if the entry that actually ends up applied at its original index has a different `RequestID` than the one it submitted — this happens when the leader loses leadership before the entry commits and a different leader's entry occupies that index instead. Implement the full `PendingWrite` lifecycle (`docs/architecture.md`) — removal on success, client cancellation/timeout, leadership loss, and node shutdown — not just the success path.
- **New-leader current-term no-op commit (I-023, `docs/architecture.md`):** upon becoming leader, reset a leader-only `readReadyTerm` gate to 0, append a no-op entry in the current term, replicate it to quorum, and require it to commit and apply — only then is `readReadyTerm` set to the current term. `GET` checks `readReadyTerm == currentTerm` as an explicit step **before** capturing a `ReadBarrier`, never relying on the ordinary barrier wait to reject on its own (the barrier is defined relative to `commitIndex`, which is exactly the not-yet-caught-up value in question, so it cannot be trusted to close this gap by itself). This closes the gap where a newly elected leader's volatile `commitIndex` may not yet reflect everything a previous leader committed, even though Leader Completeness guarantees the leader's *log* already has it.
- Read protocol per `docs/client-semantics.md`, **all three steps**: quorum leadership confirmation, read-barrier wait (`lastApplied >= readCommitIndex`), **and the term/role revalidation immediately before returning** (I-016) — this last step was the most commonly-omitted piece across this project's design history and is called out specifically for that reason. The revalidation and the KV read must be performed as one synchronized sequence under the StateMachine lock (`docs/architecture.md`'s Concurrency model / lock-ordering rule), not as a check followed by an unsynchronized read. **The quorum-confirmation round must go through the same per-follower replication lane Phase 2's replicator already owns — never a second, independently-constructed heartbeat RPC path** (`docs/architecture.md`'s "Read-confirmation heartbeats" note); this phase should not introduce a `readConfirmation.SendHeartbeat()`-shaped second sender.

## Non-goals
Replicated dedup / `RequestTable` (Phase 5 — this phase's applier calls a plain `StateMachine.Apply(cmd) (result, error)`, without dedup logic yet). Persistence hardening (Phase 4). Do not implement ReadIndex or lease reads.

## Files allowed to change (expected — additional files require Pass-1 approval)
`internal/raft/commit.go` (new), `internal/raft/apply.go` (new), `internal/raft/election.go` (extend: `readReadyTerm` gate + no-op-on-election), `internal/storage/kv_statemachine.go` (extend `Apply` call sites, add the StateMachine `RWMutex`), `internal/client/api.go` (write-blocks-until-applied + read protocol, including the `readReadyTerm` pre-check before the barrier).

## Interfaces
`leaderCommit` field now populated and propagated. `ReadBarrier{Term, CommitIndex}` per `docs/client-semantics.md`, with the mandatory post-wait revalidation step performed under the StateMachine lock.

## State changes
`NodeState.CommitIndex`, `NodeState.LastApplied` now actually driven. A new no-op entry is appended once per successful election, before the leader accepts any read-barrier wait.

## Invariants affected
I-005 (State Machine Safety), I-006 (Current-Term Commit Rule — the core of this phase, and also what makes the no-op commit work: a no-op is itself a current-term entry), I-008 (this phase implements the "minority passively adopts leaderCommit" side of I-008, not just the "cannot independently commit" side), I-009 (lastApplied ≤ commitIndex), I-010 (commitIndex ≤ lastLogIndex), I-016 (full read protocol including term revalidation, synchronized via the StateMachine lock), I-019 (request-identity-aware write completion, full `PendingWrite` lifecycle), I-023 (new-leader current-term no-op commit prerequisite for linearizable reads — new in this phase).

## Tests required
Three explicit received/replicated/committed/applied distinction tests:
1. An entry can be *replicated* to a majority before it's *committed*, if from an older term — construct deliberately.
2. An entry can be *committed* before it's *applied* on a slower follower (`lastApplied <= commitIndex`, transient nonzero gap allowed).
3. The Figure-8 scenario (I-006) as its own dedicated test.

Plus: a leader has fsynced locally but the follower ACK hasn't arrived — assert `matchIndex` has NOT advanced for that follower yet. **Read-barrier test:** construct `commitIndex > lastApplied`, assert a concurrent GET blocks until the applier catches up. **Read term-revalidation test:** start a GET's quorum confirmation, then — before the read-barrier wait completes — force the node to lose leadership or advance to a new term as leader again; assert the pending read fails/retries rather than returning a value. **Application-error-still-applies test:** commit an entry that will produce an application-level error when applied, assert `lastApplied` still advances past it and `commitIndex` is unaffected. **Write-waiter identity test (new, required, I-019):** leader appends an entry for `RequestID=abc` at index N, loses leadership before it commits; a new leader's *different* entry (different `RequestID`) ends up at index N and commits — assert the original `PendingWrite` for `abc` does NOT resolve as `SUCCESS` (it must fail/retry, surfacing as `TIMEOUT`). **`PendingWrite` cleanup test (new, required):** register a `PendingWrite`, cancel the client's context before it resolves, assert it's removed from the registry (not left registered) and a subsequent apply at that index is a no-op with respect to that abandoned waiter. **`Done`-channel non-blocking test (new, required, `docs/architecture.md`'s "Done channel safety"):** register a `PendingWrite` and never start any goroutine reading from its `Done` channel (simulating an abandoned client that never receives) — assert the applier's terminal-resolution send on `Done` still returns immediately (does not block), verifying the buffered-capacity-1 channel behaves as specified even with no reader present; run this concurrently with `go test -race` to also confirm no lock is held across a blocking operation. **New-leader no-op read test (new, required, I-023, Test A):** old leader commits a write and crashes; a new leader is elected; issue `GET` **immediately** after election, before any client write in the new term — assert it observes the old leader's committed write. **New-leader read-blocked-before-no-op test (new, required, I-023, Test B — must accompany Test A, not substitute for it):** a new leader is elected; before its no-op has committed/applied, issue a `GET` — assert it does **not** complete (blocks/retries on the `readReadyTerm` gate, before ever capturing a `ReadBarrier`) until the no-op commits and applies, at which point it completes correctly. Test A alone can pass even under a buggy implementation that relies on the ordinary read barrier instead of an explicit `readReadyTerm` gate (a fresh leader's `commitIndex=0` barrier is trivially satisfiable) — Test B is what specifically catches that bug, which is why both are required. **Exactly-one-no-op test (new, required, I-023):** trigger whatever retry/re-check logic exists around leader readiness multiple times in the same leadership term (e.g. call the no-op-ensure path twice) — assert only one `NOOP` entry for that term ever appears in the log, guarded by `leaderNoOpIndex`.

## Failure cases to handle
Advancing commitIndex using majority match-index WITHOUT the current-term restriction (Figure-8 bug). Applying entries out of order. Client write path racing the applier loop without a proper wait/notify mechanism. **Returning a read result without the post-wait term/role revalidation** — this is the specific gap flagged repeatedly in this project's design review history; treat it as the single highest-risk omission in this phase. **Serving a read from a newly elected leader before it has committed a current-term no-op** — the second highest-risk omission; a leader can pass quorum confirmation and still return a stale value if `commitIndex` hasn't caught up to what previous leaders actually committed. `PendingWrite` entries accumulating without cleanup on client timeout/cancellation or leadership loss.

## Acceptance criteria
All safety-distinction tests pass, including the new read term-revalidation test and the new-leader no-op read test. A write to the leader is visible via GET on the leader immediately after the client call returns. A partitioned-away former leader fails the quorum-confirmation step and cannot serve a stale read. A leader that loses leadership mid-read-barrier-wait fails/retries rather than returning a value. A `GET` issued immediately after a new leader's election observes every write the previous leader had committed.

## Interview concepts
The received/replicated/committed/applied distinction, from memory, with an example. Why "leader only commits current-term entries directly" is necessary (Figure 8). Why quorum confirmation *and* the apply-barrier wait *and* a final term/role recheck are all three required for a linearizable read — and what specifically breaks if any one of the three is dropped (this is now a well-rehearsed talking point given the project's own documentation history of catching this omission). Why Leader Completeness alone (I-004) doesn't make a fresh leader's reads safe, and why a current-term no-op closes that gap (I-023).
